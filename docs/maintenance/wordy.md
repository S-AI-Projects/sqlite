# Wordy exercise file map

This note records how the Wordy exercise paths are configured, how its tests
load the generated case data, and which files are generated.

## Configured files

The exercise metadata is `exercises/practice/wordy/.meta/config.json`. Its
`files` entries are relative to the exercise directory:

| Config key | Configured path | Purpose |
|---|---|---|
| `solution` | `wordy.sql` | Learner solution stub |
| `test` | `wordy_test.sql` | SQLite test runner script |
| `example` | `.meta/example.sql` | Maintained reference implementation |

There is no `editor` entry in the current config. A path validator should
validate every declared path, including an editor path if one is added, and
reject traversal or resolution outside the exercise directory.

## How tests and the reference are found

The track's `bin/verify-exercises` reads `files.example` from
`.meta/config.json`, moves the existing `<exercise-slug>.sql` solution to a
backup, copies the example into that slug-named path in place, and invokes
`bin/verify-exercise-example`. After the runner returns, it restores the
solution from the backup. This track command does not create a temporary copy
of the exercise. For Wordy, the slug path is `wordy.sql`, which also matches
`files.solution`. The runner invokes `wordy_test.sql` by slug convention; it
does not select that test script from `files.test`. In that script,
`create_fixture.sql` loads the fixture, the solution is read, and
`create_test_table.sql` is loaded using `.read ./create_test_table.sql`. That
relative `.read` is why the test table file must be present in the exercise
working directory.

The R08-T028 checker uses the configured solution, test, and example paths
directly. It copies the complete exercise, including hidden files, into a
temporary directory and substitutes the reference only for the copied
solution. It validates configured paths as files inside the exercise root and
does not rewrite the learner's working solution.

## CSV import diagnostics

The current checker run records 27 SQLite warnings from importing `data.csv`:
each row has two fields for a three-column fixture table, so SQLite fills the
remaining column with `NULL`. These warnings are non-fatal and did not affect
the tests: SQLite exited successfully, and all 27 results matched their
expected values. The checker records the warning count and this assessment in
`work/R08-T028/verification.json`.

## Maintained versus generated files

- `wordy.sql`, `.meta/example.sql`, `.meta/config.json`, `.meta/tests.toml`,
  `wordy_test.sql`, and `create_fixture.sql` are maintained exercise files.
- `create_test_table.sql` and `data.csv` are generated by `bin/generate_tests`
  from the canonical problem-specification cases, `.meta/tests.toml`, and the
  exercise's `.meta/template.create_test_table.j2` and `.meta/template.data.j2`.
  The generator writes these outputs only when their matching templates exist.
- `.meta/example.sql` is the maintained reference; it is not generated by
  `bin/generate_tests`.
- `output.json` and `user_output.md` are runtime outputs produced while running
  the exercise tests.
