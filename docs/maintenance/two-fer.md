# Two Fer test data and generation

## Canonical case source

The three cases originate in
[`exercism/problem-specifications` `canonical-data.json`](https://github.com/exercism/problem-specifications/blob/84a96854db1bda581317164d3e6ac6aa01723182/exercises/two-fer/canonical-data.json).
`bin/generate_tests` reads canonical cases from
`$XDG_CACHE_HOME/exercism/configlet/problem-specifications/exercises/two-fer/canonical-data.json`
(or `$HOME/.cache/...` when `XDG_CACHE_HOME` is unset), then filters them using
the UUIDs and `include` values in `.meta/tests.toml`.

| UUID | Description | Canonical input | Expected output |
| --- | --- | --- | --- |
| `1cf3e15a-a3d7-4a87-aeb3-ba1b43bc8dce` | no name given | `name = null` (rendered as an empty string) | `One for you, one for me.` |
| `b4c6dbb8-b4fb-42c2-bafd-10785abe7709` | a name given | `name = "Alice"` | `One for Alice, one for me.` |
| `3549048d-1a6e-4653-9a79-b0bda163e8d5` | another name given | `name = "Bob"` | `One for Bob, one for me.` |

The descriptions and UUIDs are maintained in `.meta/tests.toml`. The
`two-fer_test.sql` file contains the SQL harness rows and their expected output
strings. Those expected output strings are not rendered by the data template.

## What the repository generator does

`bin/generate_tests` accepts exercise slugs as positional arguments and has a
`--no-pull` option. From the repository root, the supported invocation for
this exercise is:

```sh
python3 bin/generate_tests --no-pull two-fer
```

The generator loads the canonical file from the problem-specifications cache
and renders outputs only for recognized templates with matching files:

* `.meta/template.data.j2` renders `data.csv`, with each canonical input name
  and an empty response field.
* There is no `.meta/template.create_test_table.j2`, so this exercise does not
  get a generated `create_test_table.sql` from this generator.
* The generator only considers `create_test_table.sql` and `data.csv`. There
  is no `.meta/template.test_reporter.sql.j2`; `test_reporter.sql` is not
  generated by `bin/generate_tests`.
* `two-fer_test.sql` and `test_reporter.sql` are maintained SQL files; the
  generator does not generate them.

## `tests.toml` sync evidence

The header in `.meta/tests.toml` explicitly says that regenerating the file
via `configlet sync` recreates `description` and `reimplements` entries,
removes `include = true`, and preserves other keys. The repository README
documents installing configlet with `./bin/fetch-configlet` and running
`./bin/configlet lint`; it does not document the path/options for a `sync`
invocation. The scheduled configlet-sync workflow sets `sync_tests: false`,
so it does not establish that this workflow updates `tests.toml`. Therefore,
the confirmed command name is `configlet sync`; no additional flags or
workflow invocation are asserted here.

## Reproducibility limits and check

Canonical data is not checked into this track repository; the standard
generator depends on a separate problem-specifications checkout/cache. A
regeneration result can therefore vary if that external input changes. The
recorded R08-T022 check input is pinned to commit
`84a96854db1bda581317164d3e6ac6aa01723182`; see
[`work/R08-T022/canonical-data.json`](../../work/R08-T022/canonical-data.json)
and [`verification.json`](../../work/R08-T022/verification.json) for the input
and observed comparison.

### Dependencies and commands

The checks require Python 3.11 or newer (for the standard-library `tomllib`),
the SQLite command-line tool with `.mode json` and SQL JSON-function support,
and Jinja2 3.1.6 (used by `bin/generate_tests`). This repository has no Python
dependency manifest, so install Jinja2 into a local virtual environment:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install "Jinja2==3.1.6"
```

Run either check from the repository root with that environment's Python:

```sh
.venv/bin/python tools/course_checks/r08-t022.py --canonical-data work/R08-T022/canonical-data.json
.venv/bin/python work/R08-T022/check.py
```

`tools/course_checks/r08-t022.py` copies the exercise and the repository
generator into a temporary repository-shaped directory, places the pinned
canonical input in the cache path expected by `bin/generate_tests`, and
regenerates there. It compares temporary `data.csv` to the working file,
then runs the SQL test harness using `.meta/example.sql` substituted only in
a temporary exercise copy. Neither the learner solution nor generated
exercise files are rewritten. `work/R08-T022/check.py` also probes that the
focused check rejects an `output.json` containing only one passing result even
when the SQL case rows contain all three cases.
